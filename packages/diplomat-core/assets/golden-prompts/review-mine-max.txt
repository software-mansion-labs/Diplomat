JUDGE THE PREMISE, NOT ONLY THE DIFF. A PR can be flawless line by line and still be the wrong change, so before the technical review, and with the same rigor, answer three questions for each PR. (1) WHAT IS IT FOR: read its title, description, commits and every issue or thread it links, and state in one sentence the problem it sets out to solve. (2) WHAT DOES IT ASSUME: name the diagnosis and every assumption the approach rests on (what causes the problem, who calls this code, what the platform or a dependency guarantees, which case "cannot happen") and check each against the code yourself. The PR's own account of the cause is a claim to verify, never a fact to build on: trace the reported symptom down to where it originates. (3) IS THIS THE RIGHT FIX: does the change remove that cause, or only stop the symptom from showing? Suspect the second whenever the diff sits away from where the fault originates: a guard, a retry, a sleep or a longer timeout, a special case for the one reported input, a swallowed error, a test loosened until it passes, a cleanup after the fact. Ask what the same cause still breaks with this PR merged (another caller, the other platform through the same code, the next input of the same shape), and whether the repo already has a mechanism for this that the PR works around or duplicates. Judge the PR as a whole, even when the technical review covers only part of it or only its outstanding threads.

A PR whose premise fails is NOT clean, however well its diff is built: it is never marked ready, approved, or reported to me as clean. A wrong diagnosis or a false assumption (unless the change removes the real cause anyway), or a workaround for a cause this repo could fix where it originates, is an in-scope behavioral finding like any other, handled the way this run handles every finding, and it is at least MEDIUM, never a LOW or a nitpick, and Blocking on someone else's PR: the cause of the problem the PR claims to solve is still there, or the problem never existed. It takes the same proof as any finding: the real cause named at file:line, plus a concrete demonstration - a case that still fails with the PR applied, the assumption shown false, or the problem gone once the cause is fixed and the workaround removed. A wrong diagnosis or a false assumption also needs the real cause shown to survive the change. A pass that runs nothing demonstrates it by reading: the cause traced to file:line and the path on which the workaround only hides it. Where it is posted, anchor it on the hunk that embodies the approach, and state the real cause and what it still breaks or merely hides. A reason that holds settles it: the premise was sound after all, or the PR or a reply gives a sound reason to defer the root fix, never a reason you supply yourself. The premise then counts as held; otherwise its thread closes only once the cause is gone. Neither its demonstrating case passing nor a deferral whose reason does not hold closes it, whatever the thread rules say. On someone else's PR, when a claimed fix to any finding, or a deferral, leaves the premise failing, or a premise thread was resolved while it still fails, reply on that thread with what still fails, unless the last Diplomat reply there already answers it, rather than leaving it alone or opening a second thread. If no change to the diff can repair it (the problem does not exist, or the real fix is a decision that is not yours to make), say so at the top of your summary instead of forcing a fix. Such an unrepairable failure is still posted wherever findings are posted, but it keeps no swarm loop or run going. A workaround is the right call only when the cause is out of this repo's reach (a dependency, the OS, someone else's service) or its root fix is deferred for such a stated reason, and then the code has to say so where the workaround lives: a missing note there is a LOW in-scope behavioral finding, Non-blocking on someone else's PR, never a failed premise. An approach you would merely have designed differently, one that also removes the cause and gets no case wrong, is a preference: drop it on sight. A failed premise never cuts the technical review short, and your summary to me carries one line per PR: what it is for and whether its premise held.
